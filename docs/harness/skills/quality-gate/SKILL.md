# 门禁检查

> 检查清单：`docs/harness/workflow/gate-checklist.md`

## 触发词

`quality-gate` / 门禁检查 / 准出检查 / 检查 Gate / 能否进入下一阶段

## 执行流程

### 第一步：确定当前阶段

根据用户上下文确定当前处于哪个 Phase，需要检查哪个 Gate：

| 当前阶段 | 需检查 | 检查清单 |
|---------|--------|---------|
| Phase 1 完成（方案设计完成） | Gate 1 | 技术方案 + **开发风险评估**落盘 + Critical=0 + 人工确认 |
| Phase 2 完成（任务规划完成） | Gate 2 | 任务计划落盘 + 可执行验收 + **High 风险已映射任务** |
| Phase 3 完成（编码实现完成） | Gate 3 | 测试通过 + 覆盖率达标 + lint 无新增 |
| Phase 4 完成（CR 审查完成） | Gate 4 | CR Critical = 0 + 产物齐全（含风险评估闭环） |

### 第二步：逐项收集证据

读取 `docs/harness/workflow/gate-checklist.md` 中对应 Gate 的检查项，逐项收集：

1. **文件存在性检查**：检查产出文件是否存在
2. **内容完整性检查**：检查文件是否包含必要章节
3. **测试结果检查**（Gate 3/4）：运行测试命令，收集通过率和覆盖率
4. **lint 检查**（Gate 3/4）：运行 lint 工具
5. **一致性检查**：对比代码与方案的一致性

### 第三步：输出检查报告

```markdown
## 门禁检查报告 — Gate {N}

| 检查项 | 状态 | 证据 |
|--------|------|------|
| G{N}.1 {描述} | ✅ 通过 / ❌ 未通过 | {证据描述} |
| G{N}.2 {描述} | ✅ / ❌ | {证据} |

**结论**：✅ 可进入 Phase {N+1} / ❌ 需修复以下问题后重新检查

### 未通过项修复建议
| 检查项 | 问题 | 修复建议 |
|--------|------|---------|
```

### 第四步：更新 workflow_state

- 门禁通过 → 更新 `workflow_state.md` 中对应门禁状态为 ✅，记录通过日期
- 门禁未通过 → 告知用户需要修复的问题
