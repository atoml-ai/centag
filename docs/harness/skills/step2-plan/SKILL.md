# Step 2: 任务规划

> 执行指南：`docs/harness/workflow/phase-2-plan.md`

## 触发词

`step2-plan` / 任务规划 / 拆任务 / 拆解 / step2

## 前置门禁

**Gate 1**：技术方案落盘 + **开发风险评估落盘** + 内审 Critical = 0 + 人工确认

> ⚠️ 执行前必须先检查 Gate 1，未通过则拒绝继续。  
> 若缺少 `开发风险评估.md`，引导用户先执行 `step1-risk`，禁止直接拆任务。

## 执行流程

### 第一步：收集输入

1. 确认当前需求名称
2. 读取技术方案（`docs/versions/<版本>/<需求>/技术方案.md`）
3. **读取开发风险评估**（`docs/versions/<版本>/<需求>/开发风险评估.md`）
4. 阅读 `docs/harness/ARCHITECTURE.md` 了解模块影响范围
5. 确认用户角色和关注范围

### 第二步：任务拆解

1. 从方案中提取功能点清单
2. 将每个功能点拆解为独立任务
3. 标注任务间的依赖关系
4. 确定执行顺序
5. **风险落地**：将风险评估中每条 High/Critical（应为 0 条开放 Critical）映射到具体任务 ID；无归属的 High 禁止进入 Step 3

### 第三步：编写任务计划

按 `docs/harness/templates/任务计划模板.md` 结构编写，每个任务包含：

- 任务名称与描述
- 所属功能点
- 前置依赖
- **可执行验收标准**（必须是可验证的动作，如 `go test ./...`、`curl` 验证等）
- **执行约束**（可改/不可改的文件清单）
- **关联风险 ID**（来自 `开发风险评估.md`，无则填「无」）
- 风险缓解要点（该任务如何关闭或降低关联风险）

任务计划中必须包含章节 **「开发风险与任务映射」**（或等价表），与 `开发风险评估.md` §4 一致。

写入 `docs/versions/<版本>/<需求>/任务计划.md`

同步更新 `开发风险评估.md`：填写「归属任务」、状态改为「已缓解（设计）」或保持「开放」并说明原因。

### 第四步：人工确认

- 用户确认任务计划
- 用户确认执行顺序
- 用户确认 High 风险均已挂到任务且验收可覆盖

## 产出

| 产物 | 路径 |
|------|------|
| 任务计划 | `docs/versions/<版本>/<需求>/任务计划.md` |
| 开发风险评估（更新映射） | `docs/versions/<版本>/<需求>/开发风险评估.md` |

## 完成后

- 更新 `workflow_state.md`：Step 2 状态 → ✅ 已完成，Gate 2 → ✅（需人工确认后）
- 提示用户可执行 `step3-code` 进入编码实现阶段（将自动检查 Gate 2）。
