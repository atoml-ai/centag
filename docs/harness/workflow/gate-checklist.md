# 门禁检查清单

本文档定义了工作流门禁的完整检查条件。每个门禁为硬性约束，未通过禁止进入下一阶段。

---

## Gate 1：Phase 1 → Phase 2（方案设计 → 任务规划）

**触发时机**：用户调用 `step2-plan` 时自动检查

### 准出条件

- [ ] **G1.1** 技术方案已落盘到 `docs/versions/<版本>/<需求>/技术方案.md`
- [ ] **G1.2** 方案结构完整（背景、方案选型、接口设计、数据模型、方案级风险摘要等）
- [ ] **G1.3** **开发风险评估**已落盘到 `docs/versions/<版本>/<需求>/开发风险评估.md`，结构完整（登记表 + Critical/High 专项 + 结论）
- [ ] **G1.4** 开发风险评估中 Critical 开放数 = 0；High 均有应对与可执行验证方式
- [ ] **G1.5** AI 内审 Critical 问题数 = 0
- [ ] **G1.6** 人工已审核技术方案与开发风险评估并确认
- [ ] **G1.7** 方案中的接口设计、数据库设计与现有架构一致

### 违反时处理

| 违反项 | 处理方式 |
|--------|---------|
| G1.1-G1.2 | 补充缺失内容 |
| G1.3-G1.4 | 执行 `step1-risk` 补齐/修订开发风险评估 |
| G1.5 | 修复 Critical 问题后重新内审 |
| G1.6-G1.7 | 人工审核并修正不一致处 |

---

## Gate 2：Phase 2 → Phase 3（任务规划 → 编码实现）

**触发时机**：用户调用 `step3-code` 时自动检查

### 准出条件

- [ ] **G2.1** 任务计划已落盘到 `docs/versions/<版本>/<需求>/任务计划.md`
- [ ] **G2.2** 每个任务包含：可执行验收标准 + 执行约束
- [ ] **G2.3** 实现型任务有编码级执行步骤（Spec 追溯 → 实现 → 测试验证）
- [ ] **G2.4** 执行约束已定义（可改/不可改文件清单）
- [ ] **G2.5** `开发风险评估.md` 中每条 High 风险已映射到任务 ID，且任务验收能覆盖其验证方式
- [ ] **G2.6** 开发风险评估 Critical 开放数仍为 0
- [ ] **G2.7** 人工已确认任务计划与风险映射

### 验收标准质量要求

验收标准必须是**可执行的验证动作**：

| ✅ 正确示例 | ❌ 错误示例 |
|------------|-----------|
| `go test ./internal/... -run TestXxx` 全部通过 | 功能正常 |
| API 响应格式与方案一致 | 代码质量好 |
| lint 无新增警告 | 没有明显 bug |
| 覆盖率 ≥ 80% | 测试充分 |

---

## Gate 3：Phase 3 → Phase 4（编码实现 → 质量交付）

**触发时机**：用户调用 `step5-review` 时自动检查

### 准出条件

- [ ] **G3.1** 全量单元测试通过
- [ ] **G3.2** 测试覆盖率达到项目规定阈值
- [ ] **G3.3** lint 无新增警告
- [ ] **G3.4** 所有人工检查点已确认通过

### 违反时处理

| 违反项 | 处理方式 |
|--------|---------|
| G3.1-G3.3 | 回到 Phase 3 修复代码或测试 |
| G3.4 | 回到对应任务的检查点重新确认 |

---

## Gate 4：Phase 4 → Phase 5（CR 准出 → 可发版）

**触发时机**：

1. Step 5 结束时：征求人工确认（AskQuestion），通过后将 Gate 4 标 ✅  
2. 用户调用 `step6-release` 时：**再次自动检查**；未通过则拦截发版

### 准出条件

- [ ] **G4.1** CR 报告中 Critical 问题数 = 0（含修复后增量审查）
- [ ] **G4.2** 全量测试通过
- [ ] **G4.3** 测试覆盖率达标
- [ ] **G4.4** 代码与技术方案一致
- [ ] **G4.5** 所有标准产物已落盘（技术方案 + **开发风险评估** + 任务计划 + 自测记录 + CR 报告 + 代码 + 测试）
- [ ] **G4.6** 开发风险评估无开放 Critical；High 均为已关闭或文档化可接受残余
- [ ] **G4.7** **人工已确认「批准 — 可发版」**（写入 CR 结论 + `workflow_state` Gate 4 = ✅）

> G4.7 为发版硬门禁：仅完成 CR 文档、未获人工批准 → Gate 4 不得为 ✅，`step6-release` 必须拒绝。

### 违反时处理

| 违反项 | 处理方式 |
|--------|---------|
| G4.1 | 在 Step 5 中修复缺陷后增量审查 |
| G4.2-G4.3 | 回到 Phase 3 修复 |
| G4.4 | 同步代码或方案 |
| G4.5 | 补齐缺失产物 |
| G4.6 | 关闭或文档化残余风险 |
| G4.7 | 回到 Step 5 第四步，AskQuestion 确认批准 |

---

## Gate 5：发版准出

**触发时机**：Step 6 发版验收完成时检查

### 准出条件

- [ ] **G5.1** GitHub Release `v<version>` 已创建（草稿或已发布，按约定）
- [ ] **G5.2** 资产齐全：`centag-personal-*`、`centag-wrap-*`（约定平台）+ `checksums.txt`
- [ ] **G5.3** 版本分支门禁在发版时已通过
- [ ] **G5.4** 安装冒烟通过，或用户明确跳过并记入 `workflow_state` 决策日志
- [ ] **G5.5** `workflow_state`：Step 6 = ✅

### 违反时处理

| 违反项 | 处理方式 |
|--------|---------|
| G5.1-G5.3 | 留在 Step 6 修复上传/分支问题 |
| G5.4 | 补做冒烟或记录跳过原因 |
| G5.5 | 更新状态文件 |

---

## 门禁触发机制

| 触发场景 | AI 行为 |
|---------|---------|
| 用户调用跨 Phase 的 step 别名 | 自动检查前置门禁，未通过则拦截并列出缺失项 |
| 用户显式说"检查门禁" | 逐项收集证据并输出检查报告 |
| Phase 内正常操作 | 不触发门禁 |
| `step6-release` / 发版 | **强制**检查 Gate 4（含 G4.7） |

### 检查流程

```
用户调用 step{N} 别名
       │
       ▼
AI 读取 workflow_state.md 确认当前 Phase
       │
       ├── 同 Phase 内 → 直接执行
       │
       └── 跨 Phase → 自动触发前置门禁检查
                │
                ├── ✅ 通过 → 更新 workflow_state → 执行
                └── ❌ 未通过 → 告知缺失项 → 拒绝继续
```
