## 3. Critical / High 专项

### R03 — 架构边界违规（Critical）

- **触发条件**：在 `core/internal/` 直接新增 team 多租户专有逻辑（而非通过插件/扩展点）。
- **最坏结果**：核心层与闭源业务耦合，开源核心无法独立编译/分发，违反 Open Core 前提。
- **缓解措施（编码前可做）**：team 增值全部经 `BusinessPlugin` 注册（`business.Register()`）与管理接口（`/api/v1/admin/*`，按 CAPABILITY_BOUNDARY 允许）接入；核心层零修改或仅增接口契约（不含实现）。
- **验证方式（可执行）**：`rg -l "centag-business" core/` 应为空（核心不得反向依赖闭源仓）；`go build ./dist/team`（不开 business_team tag）必须成功且不含私有代码。
- **残余风险**：可接受。

### R01 — 开源 team 构建拉取私有代码（High）

- **触发条件**：`dist/team/main.go` 直接 `import "example.com/.../centag-business"` 而无 build tag 隔离。
- **最坏结果**：开源用户 `go build ./dist/team` 因无法访问私有仓而失败，违背"免费版真正开源"。
- **缓解措施（编码前可做）**：business 插件 import 包在 `//go:build business_team` 文件内；默认（无 tag）使用开源 stub 文件（同包名、空实现、`//go:build !business_team`）。
- **验证方式（可执行）**：`GIT_EXEC_PATH=... go build -tags '' ./dist/team` 成功；`go build -tags 'business_team' ./dist/team`（需 replace 私有仓）成功。
- **残余风险**：可接受。

### R02 — 跨仓版本漂移（High）

- **触发条件**：核心仓升级接口但闭源仓 `go.mod` 未同步。
- **最坏结果**：team 构建中断或运行时契约错误。
- **缓解措施（编码前可做）**：闭源仓 `go.mod` 锁核心仓具体 tag/commit；建立双向 CI（核心变更触发闭源仓构建校验）。
- **验证方式（可执行）**：闭源仓 CI `go build ./...` 在核心发布新 tag 时自动跑。
- **残余风险**：可接受。

### R05 — 许可证传染（High）

- **触发条件**：核心仓采用 GPL/AGPL 等 copyleft 协议。
- **最坏结果**：闭源仓链接核心后被迫开源，商业化失效。
- **缓解措施（编码前可做）**：核心仓采用 MIT（推荐）或 Apache-2.0；两者均允许闭源产品依赖且不传染。
- **验证方式（可执行）**：LICENSE 文件头声明为 MIT；`grep -i "GPL\|AGPL" LICENSE` 为空。
- **残余风险**：可接受。
