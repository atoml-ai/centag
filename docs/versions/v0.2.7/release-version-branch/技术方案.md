# 技术方案 — 发版仅限版本分支

> 版本：v0.2.7 | 需求：release-version-branch | 日期：2026-07-21

## 背景

GitHub Release 上传曾限制在 `main`。实际发版在版本分支（如 `feature/v0.2.7`）完成，再合入 main；因此门禁改为「仅版本分支可发版」，并与 `install.sh` / Release 资产流程对齐。

## 方案选型

| 方案 | 说明 | 结论 |
|------|------|------|
| A. 仅 main | 与当前发版习惯冲突 | 否 |
| B. 版本分支 `vX` / `feature/vX` / `release/vX` | 与分支命名约定一致 | **采用** |
| C. 任意分支 + 人工 | 易误发 | 否（仅紧急旁路） |

## 接口 / 行为设计

- 本地：`scripts/release/require-release-branch.sh --version <X>`；当前分支必须是允许集合之一。
- CI：`--ci`；`workflow_dispatch` 校验 `GITHUB_REF_NAME`；`push`+tag 校验 tag 版本且 commit 在对应版本分支历史上。
- 紧急旁路：`CENTAG_RELEASE_ALLOW_ANY_BRANCH=1`（文档警告，非正式路径）。
- `require-main-branch.sh` 保留为弃用转发。

## 数据模型

无。

## 方案级风险摘要

- 误在 main 发版被拒 → 预期行为。
- tag 不在版本分支历史 → CI 拒绝（防从错误 commit 打 tag）。
- 本地 ahead/behind remote → warn 或 fail，避免 install.sh raw URL 与已发布资产不一致。
