# 技术方案 — Prompt 策略（prompt-strategy）

> 版本：v0.3.1 | 日期：2026-07-25 | 作者：AI  
> 分支：承载于 `feature/v0.3.1`（或发布列车分支）  
> 范围：system / user / 输出后处理三阶段；**不区分流水线**；分阶段落地（框架 + 基础能力优先，预留专用 LLM）

## 1. 背景与目标

### 1.1 问题描述

Centag 作为 LLM 网关，对客户端 `system` / `user` 消息与模型输出的处理语义目前**割裂且偏硬编码**：

| 维度 | 现状 | 痛点 |
|------|------|------|
| System | `#t` 透传；`#d`/`generator` 非空 `system_prompt` 时**无条件替换**；**无 append** | 企业常需「保留客户端 system + 追加规范」（如「输出使用中文」「标准 JSON」）；无法按场景统一配置 |
| User | 无一等「入站检查 / 精简」能力；`#t/#d` 以 `raw_request_body` 为准，仅改 Messages 对透传无效 | 敏感词、数据泄漏风险、冗长 prompt 无法在网关侧规范化 |
| 输出 | 有 `processor` / `optimize` / `summarizer` 等 LLM 后处理链，但缺轻量「JSON 规范化 / 字符级清洗」统一框架 | 字符串级后处理与 LLM 后处理混用成本高；无法声明式挂载 |
| 双路径 | `transparent_forward` 与 `generator` 各自实现 system 注入，语义略有差异（模板渲染仅 generator） | 策略扩展易漂移；契约测试需两边对齐 |

钩子（`core/pkg/hooks`、Pipeline StorageHook）负责计量/落库，**不适合**作为 prompt 改写主路径。垂直能力应按能力边界落在**可编排流水线节点 / BusinessPlugin**。

### 1.2 目标

| # | 目标 | 验收要点 |
|---|------|----------|
| G1 | 统一 **Prompt Strategy 框架**：system / user / output 三阶段可配置 | 配置契约稳定；任意流水线可挂载，不绑死某一 `X-Proxy-Mode` |
| G2 | System 三种策略：`passthrough` / `append` / `replace` | 与现有 `inject_system_prompt` 兼容映射；`#t/#d` 与 `generator` 行为一致 |
| G3 | User：基础检查（敏感/泄漏启发式）+ 基础优化（截断/精简规则） | Phase A 纯规则；Phase B 预留 LLM 槽位 |
| G4 | Output：基础后处理（JSON 抽取/规范化、空白整理等） | Phase A 字符串算子；Phase B 预留 LLM 摘要/改写 |
| G5 | **分阶段**：先框架 + 字符串/规则能力；LLM 预处理/后处理以接口占位接入，有条件时引入专用模型服务 | 占位接口可编译、可配置、默认 no-op；不阻断主路径 |
| G6 | **Web 配置必做**：画布节点抽屉可完成 System / User / Output 配置与联调验收 | 按 [`前端配置操作说明.md`](./前端配置操作说明.md) 手工走通；无 Web 不得宣称 Phase A 完成 |

### 1.3 非目标（本版 / Phase A）

- 不新增面向 Agent 的业务专用 HTTP 路由（仍走 `/v1/chat/completions`、`/v1/messages`、`/v1/responses`）。
- 不在 `mode_dispatcher` / HTTP handler 硬编码垂直策略分支。
- 不把 prompt 改写塞进 `core/pkg/hooks` 主路径。
- Phase A **不实现**完整 LLM 预检/精简/后处理模型调用（只留接口 + 配置位 + 可选 stub）。
- **不做**独立「策略中心」全局页或全新策略 IDE；配置落在现有**画布 + 节点配置抽屉**（Web **必做**，见 G6）。
- 不强制改写所有存量模板为新节点拓扑；兼容旧布尔字段即可渐进迁移。
- 不做跨租户策略市场 / 策略包分发（可后续）。

## 2. 方案选型

### 2.1 候选方案对比

| 方案 | 优点 | 缺点 | 推荐 |
|------|------|------|------|
| A. 仅扩展 `inject_system_prompt` 布尔 → 枚举，user/output 另起炉灶 | 改动面最小 | 三阶段不一致；user/output 仍缺框架 | |
| B. **统一 Prompt Strategy 契约 + 共享算子库**；system 嵌入现有出站节点；user/output 用独立可编排节点；LLM 经 BusinessPlugin/Capability 占位 | 与架构边界一致；可分阶段；任意流水线可挂 | 需统一双路径与 raw body | ⭐ |
| C. 单一巨型 `prompt_guard` 中间件挂在 proxy 入口 | 一处改全站 | 违反薄核心；难按流水线差异化；难测 | |

### 2.2 选定方案

采用 **方案 B**：

1. **契约层**：定义 `SystemPromptStrategy` / `UserPromptOps` / `OutputPostOps` 配置与执行接口（`core/pkg/pipeline/promptstrategy/` 或同级包）。
2. **System**：在 `transparent_forward` 与 `generator` **共用同一算子**，消灭双路径语义漂移；兼容 `inject_system_prompt`。
3. **User / Output**：以 **builtin 节点**（规则/字符串）接入流水线；LLM 能力通过 `PromptLLMProcessor` 接口占位，后续接专用后端或 BusinessPlugin。
4. **编排位置**：不区分流水线类型——模板作者在需要处声明策略；默认模板保持现有行为（透明透传 / 直连 replace）。

## 3. 详细设计

### 3.1 总体数据流

```mermaid
flowchart LR
  Client[客户端请求] --> In[协议入站 / PipelineInput]
  In --> U[User Prompt Ops<br/>check / optimize]
  U --> S[System Prompt Strategy<br/>passthrough / append / replace]
  S --> LLM[出站 LLM<br/>transparent_forward / generator]
  LLM --> O[Output Post Ops<br/>normalize / trim / JSON]
  O --> ClientOut[响应客户端]
```

说明：

- User 阶段在出站**之前**；改写须同步 `Messages`、`Content`，以及对 `transparent_forward` 同步 `metadata.raw_request_body`。
- System 阶段可在出站节点内执行（与今日 inject 同位置），也可由前置节点改写后交给「空策略」出站；**推荐出站节点内调用共享算子**，减少模板强制插入节点。
- Output 阶段在生成节点之后串行；流式场景 Phase A 默认「缓冲完整文本再处理」或「仅非流式启用」（见风险 R03）。

### 3.2 System Prompt 策略

#### 3.2.1 枚举

| 策略 | 语义 | 典型用途 |
|------|------|----------|
| `passthrough` | **不改**客户端 system；忽略节点/网关 `system_prompt` 文本（或仅作文档提示） | 透明代理 `#t`、跳板 `#j` |
| `append` | 保留客户端全部 system；将网关文本 **追加**（默认新 system 消息置于客户端 system 之后；可配置 `append_position: after_client \| before_client \| merge_last`） | 「在原 prompt 后加：输出使用中文 / 标准 JSON」 |
| `replace` | 丢弃客户端 system，使用网关渲染后的 `system_prompt` | 直连 `#d`、教育/场景包强管控 |

默认兜底：未配置策略时，保持**今日行为**：

- `inject_system_prompt: false`（或缺省）→ `passthrough`
- `inject_system_prompt: true` 且网关 prompt 非空 → `replace`
- `generator`：节点/全局 `system_prompt` 非空 → `replace`；空 → `passthrough`

#### 3.2.2 配置形态

```yaml
# 节点 config / custom_config（推荐字段）
system_prompt: |
  你是企业知识助手……
# 新字段（优先）
system_prompt_strategy: passthrough | append | replace   # 缺省按兼容映射
append_text: |                                            # 可选；append 时若与 system_prompt 二选一/合并规则见下
  输出使用中文。以标准 JSON 格式输出。
append_position: after_client                             # Phase A 支持 after_client / before_client
# 兼容旧字段（继续识别）
custom_config:
  inject_system_prompt: true   # → replace；false → passthrough
```

**append 文本来源优先级（Phase A）**：

1. `append_text`（若非空）  
2. 否则 `system_prompt`（节点 → `global_config.system_prompt`）  
3. 二者皆空 → 等价 `passthrough`（打 debug 日志）

**replace 文本来源**：同现网（节点 `system_prompt` → global）；`generator` 继续支持 Go template 渲染；`transparent_forward` Phase A **对齐**可选轻量模板渲染（或文档标明「仅字面量」，见风险），推荐 Phase A 对 forward 也调用同一 `RenderSystemPrompt` helper，避免长期双轨。

#### 3.2.3 共享算子（伪接口）

```go
// package promptstrategy
type SystemMode string // passthrough | append | replace

type SystemApplyInput struct {
    Mode           SystemMode
    GatewayPrompt  string          // 已渲染
    AppendPosition string
    Messages       []Message       // chat 消息视图
    RawBody        []byte          // 可选；chat JSON
}

type SystemApplyResult struct {
    Messages []Message
    RawBody  []byte // 若入参有 RawBody 则同步写出
    Applied  bool
    Mode     SystemMode
}

func ApplySystemStrategy(in SystemApplyInput) (SystemApplyResult, error)
```

`transparent_forward` 将现有 `injectSystemPromptIntoChatBody` 升级为调用 `ApplySystemStrategy`（含 append）；`generator` Execute / ExecuteStream 同步调用。

#### 3.2.4 Responses API

今日 inject **跳过** Responses 体（`input` / `instructions`）。Phase A：

- Chat `messages`：完整支持三策略。  
- Responses：  
  - `passthrough`：不变；  
  - `replace` / `append`：**占位**——优先改写 `instructions`（若存在），否则在 `input` 数组前插入/追加 system 角色项；契约测试覆盖；若形态无法安全改写则 **fail-open 保持原样 + 指标/日志**，避免破坏 OpenCode/Codex。

### 3.3 User Prompt 操作

#### 3.3.1 能力分层

| 操作 | Phase A（基础） | Phase B（框架占位 → 实装） |
|------|-----------------|---------------------------|
| 检查 | 规则：敏感词表、密钥形态启发式（AK/SK、Bearer、私钥头）、超长、禁止模式 | LLM 安全分类 / 企业策略引擎（专用模型服务） |
| 优化 | 规则：空白折叠、最大长度截断、可选去重复行 | LLM 精简/改写（专用小模型） |
| 处置 | `action: log \| redact \| block \| pass` | 同左；block 返回网关统一错误结构 |

#### 3.3.2 节点：`builtin.user_prompt_ops`（名称可定为 `user_prompt_ops`）

```yaml
- id: user_guard
  type: user_prompt_ops          # 或 implementation: builtin.user_prompt_ops
  config:
    custom_config:
      check:
        enabled: true
        deny_patterns: ["(?i)sk-[a-z0-9]{20,}"]
        keyword_list_ref: enterprise_sensitive_v1   # 可选；本地内置小表 + 配置路径
        on_hit: redact          # log | redact | block
      optimize:
        enabled: true
        max_user_chars: 32000
        collapse_whitespace: true
      # Phase B 占位（Phase A 忽略或 no-op）
      llm:
        enabled: false
        capability: prompt.preprocess   # CapabilityBroker 槽位名（预留）
        backend: "{{system.default_backend}}"
        model: ""
        mode: check_then_optimize       # 预留枚举
```

执行要点：

1. 定位「最后一条 user」及 `input.Content`；多轮时默认只处理最后 user（可配置 `scope: last_user | all_user`）。  
2. 若存在 `raw_request_body`，**必须**同步改写 JSON `messages`（及 Responses 对应 user 段），否则 `#t/#d` 无效。  
3. `block`：返回可识别错误码（建议 `prompt_strategy_blocked`），不发起后端调用。  
4. 日志默认 **脱敏预览**（复用现有 `MaskSensitiveData`）。

#### 3.3.3 LLM 预处理占位

```go
type PromptLLMProcessor interface {
    Name() string
    Process(ctx context.Context, req PromptLLMRequest) (PromptLLMResponse, error)
}

type PromptLLMRequest struct {
    Stage   string // "user_check" | "user_optimize" | "output_post"
    Text    string
    Config  map[string]any
}

// Phase A: NullPromptLLMProcessor（enabled=false 或未注册时）
```

注册点：CapabilityBroker 能力名预留 `prompt.preprocess` / `prompt.postprocess`；外部仓或后续版本提供实现。**禁止** Phase A 在核心内嵌死某一厂商调用。

### 3.4 输出后处理

#### 3.4.1 节点：`builtin.output_post_ops`

```yaml
- id: out_normalize
  type: output_post_ops
  config:
    custom_config:
      ops:
        - trim_space
        - strip_markdown_fence   # ```json ... ```
        - extract_json           # 复用/抽取 cleanJSONContent
        - json_compact           # 合法 JSON 则重新 Marshal
      on_invalid_json: pass      # pass | wrap_error_object
      llm:
        enabled: false
        capability: prompt.postprocess
        mode: summarize | rewrite | json_repair   # 预留
```

与现有 `processor`/`optimize`/`summarizer` 关系：

- **字符串算子** → `output_post_ops`（轻、默认可关）。  
- **LLM 后处理** → 继续用现有 business 节点；或 Phase B 经 `PromptLLMProcessor` 统一入口。  
- Phase A **不删除**旧节点；新节点是规范化补齐，而非替代全部 LLM 链。

#### 3.4.2 流式

| 模式 | Phase A |
|------|---------|
| 非流式 | 完整支持 ops |
| 流式 | 默认跳过字符串规范化（透传 chunk）；配置 `stream_mode: skip \| buffer`；`buffer` 聚合后再处理（延迟升高，需文档标明） |

### 3.5 模板与默认行为（兼容）

| 模板 / 模式 | Phase A 变更 |
|-------------|--------------|
| `transparent-proxy` | 显式 `system_prompt_strategy: passthrough`（或继续依赖 inject=false） |
| `direct-backend` | `system_prompt_strategy: replace`（或 inject=true 兼容） |
| `fixed-egress` | passthrough |
| 教育/编码等 generator 场景包 | 默认仍 replace；可选改为 append + 规范尾巴 |
| 任意自定义流水线 | 可在出站前插入 `user_prompt_ops`、出站后插入 `output_post_ops` |

**不强制**一次性改完所有 YAML；契约测试锁定 `#t/#d/#j` 不回归。

### 3.6 接口与配置（管理面）

本版**不新增** Agent 业务 API。配置面以 **Web 画布 + 节点抽屉为 Phase A 必交付**（验收与联调入口）：

| 项 | 优先级 | 说明 |
|----|--------|------|
| Web · System 策略 | **P0 必做** | `NodeConfigDrawer`：布尔「注入」升级为透传/追加/替换；追加文本框、替换提示词区 |
| Web · User / Output 节点 | **P0 必做** | 插件面板可添加；抽屉表单按操作说明 §5 / §6；保存写回 pipeline JSON |
| Web · LLM 占位控件 | P1 | 开关禁用 +「后续版本」文案即可 |
| Pipeline YAML / Admin PUT | P0（既有） | `PUT /api/v1/pipelines/:id` 热加载；Web 只是编辑器 |
| 文档 | P0 | `docs/guide/` + [`前端配置操作说明.md`](./前端配置操作说明.md) |

**验收约束**：后端能力对齐后，必须能在 Web 上完成操作说明 §10 五步手工验收；仅 YAML/API 不算 Phase A 完成。

### 3.7 数据模型

- **无强制 DB schema 迁移**。策略存在流水线节点 JSON/YAML。  
- 可选后续：敏感词表文件 `config/profiles/<edition>/prompt-strategy/denylist.txt`（Phase A 可用内置最小集合 + 配置路径覆盖）。

| 模块 | 变更 |

### 3.9 分阶段实施路线

| 阶段 | 内容 | 出口标准 |
|------|------|----------|
| **A0 框架** | 包结构、枚举、兼容映射、`ApplySystemStrategy`、双路径接线、契约测试 | `#t` 透传 / `#d` replace 零回归；append 单测绿 |
| **A1 User 基础** | `user_prompt_ops` 规则检查 + 截断；raw body 同步；block 错误码 | 集成测试覆盖透传路径 |
| **A2 Output 基础** | `output_post_ops` 字符串算子；非流式默认 | JSON fence 用例绿 |
| **A3 文档/模板** | guide + 可选模板示例（append 中文/JSON） | harness 文档链接 |
| **A4 Web 配置（必做）** | System 三选一 UI；User/Output 节点可添加可保存；中英文案 | 操作说明 §10 五步在浏览器走通；`npm run lint:ci` |
| **B1 LLM 占位接线** | Capability 注册名、配置开关、Null 实现、指标；Web 禁用开关 | enabled=false 无额外延迟 |
| **B2 专用模型服务** | 外部实现 preprocess/postprocess；可选独立后端槽位 | 企业开关验证 |

Phase A（**A0–A4**）为 v0.3.1 建议交付范围（含 Web）；B1 可同版本「接口落盘」，B2 可后续版本。

### 3.10 观测与安全

- Metrics（建议）：`prompt_strategy_system_applied{mode}`、`user_prompt_ops_hit{action}`、`output_post_ops{op}`、`prompt_llm_skipped`。  
- 日志：只打脱敏 preview；命中 redact/block 记原因码，不记完整密钥原文。  
- Fail-open vs fail-closed：规则解析失败默认 fail-open（透传）+ 错误计数；`on_hit: block` 为显式 fail-closed。

## 4. 兼容性与迁移

| 项 | 策略 |
|----|------|
| `inject_system_prompt` | 继续支持；与 `system_prompt_strategy` 同时存在时 **strategy 优先**，并 debug 日志提示 |
| 空 `system_prompt` + replace | 等价 passthrough（与今日「有文本才替换」一致） |
| 旧流水线无新节点 | 行为不变 |
| Responses | 见 3.2.4；不能改则透传 |
| 发行版 | minimal / personal / team 均可用框架；敏感词表可按 profile 覆盖 |

迁移建议：新场景优先写 `system_prompt_strategy`；存量模板随版本火车逐步标注，不强制 big-bang。

## 5. 风险与应对（方案级摘要）

> 开发实现风险详见同目录 `开发风险评估.md`。

| 风险 | 影响 | 概率 | 应对策略 |
|------|------|------|---------|
| 双路径（forward / generator）语义漂移 | 同配置不同行为 | 中 | 强制共享算子 + 契约测试矩阵 |
| raw_request_body 未同步 | `#t/#d` 策略失效 | 高 | User/System 改写必经 body sync helper |
| append 破坏多 system Agent 客户端 | 工具链异常 | 中 | 默认 after_client；契约 + 真实客户端抽检 |
| 流式后处理延迟 | 体验下降 | 中 | Phase A 默认 skip；buffer 显式开启 |
| LLM 阶段范围膨胀 | 排期失控 | 中 | B1 仅占位；B2 另版本 |

## 6. 附录

### 6.1 与能力边界对齐
