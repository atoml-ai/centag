## 3. Critical / High 专项

### R01 — OpenAI `response_format` / `tool_choice` 解析错误导致请求被静默丢弃

- **触发条件**：客户端发送畸形 `response_format`（如缺少 `type` 字段）或 `tool_choice` 为不支持的 JSON 结构。
- **最坏结果**：解析失败 → 不进入 RawBody 透传路径 → 请求到达后端时缺失这些字段 → 后端按默认行为处理（可能非客户端预期）。
- **缓解措施（编码前可做）**：
  1. `ParseRequest` 中新增字段解析失败时记录 Warn 日志，但不返回错误。
  2. 原始 `rawBody` 始终保留，`RawBody` 在后端转发时作为基础请求体，显式字段仅做覆盖。
- **验证方式（可执行）**：
  ```bash
  go test ./plugins/protocol/openai/ -run TestParseRequest_ResponseFormat -v
  go test ./plugins/protocol/openai/ -run TestParseRequest_ToolChoice -v
  ```
- **残余风险**：可接受

### R05 — `ModeDispatcher` 构造 `proxyReq` 时遗漏新增字段

- **触发条件**：`handler.go` 中 `proxyReq` 构造时忘记拷贝新增字段（如 `ResponseFormat`、`ToolChoice`）。
- **最坏结果**：协议插件已解析出的字段在 ModeDispatcher 入口被丢弃 → 后端收不到 `response_format` → 客户端请求 JSON Mode 但后端返回普通文本。
- **缓解措施（编码前可做）**：
  1. 技术方案中明确列出 `proxyReq` 构造的字段清单，编码时按清单逐项拷贝。
  2. 在 `proxy/handler.go` 新增 `copyProxyRequestFields(req *plugin.ProxyRequest)` 辅助函数，集中管理字段拷贝，避免分散遗漏。
- **验证方式（可执行）**：
  ```bash
  go test ./core/internal/proxy/ -run TestProxyRequestFieldCopy -v
  rg 'proxyReq := &plugin.ProxyRequest' ./core/internal/proxy/ -A 20  # review 字段拷贝完整性
  ```
- **残余风险**：可接受

### R11 — 排期膨胀：字段数量多，编码阶段范围蔓延

- **触发条件**：编码过程中顺手补齐 P2 字段（`logprobs`、`audio`、`modalities`、`metadata`、`top_k` 等），导致任务量增加、测试覆盖不足。
- **最坏结果**：本版本交付延期；P2 字段因测试不充分引入 regression。
- **缓解措施（编码前可做）**：
  1. 技术方案附录中明确 P0/P1/P2 字段优先级，Step 2 任务规划中严格按优先级拆解任务。
  2. [修订 L3/G7] P2 字段仅在协议请求结构体占位（`omitempty`）+ 经 `RawBody` 透传至后端；**不映射 ParseRequest、不进 `ProxyRequest.Metadata`、不进 `handler.copyProxyRequestFields`、不进缓存 key**。Handler/Format 逻辑暂不实装，留待 v0.2.9。
- **验证方式（可执行）**：
  ```bash
  rg 'P2' ./docs/versions/v0.2.8/protocol-alignment/技术方案.md
  # P2 字段不应出现 ParseRequest 映射行（Modalities/TopK/Logprobs 作为 ProxyRequest 赋值左侧应为 0 行）
  rg 'ProxyRequest\.(Modalities|TopK|Logprobs)\b' plugins/protocol/openai/protocol.go plugins/protocol/anthropic/protocol.go core/internal/proxy/handler.go
  ```
- **残余风险**：可接受

### R12 — `MessageContent` 自定义 UnmarshalJSON 对 vision 数组解析不健壮

- **触发条件**：客户端发送 vision 消息（`content: [{"type":"image_url","image_url":{"url":"..."}}]`），当前 `UnmarshalJSON` 将其解析为 `[]map[string]interface{}`，但 `String()` 方法只提取 `type:text` 的文本，丢弃图片内容。
- **最坏结果**：图片输入被静默丢弃 → 后端只收到空消息或纯文本 → 模型输出异常。
- **缓解措施（编码前可做）**：
  1. 扩展 `MessageContent` 的 `UnmarshalJSON` / `MarshalJSON` / `String()`，支持 vision 内容数组的完整保留。
  2. `ProxyRequest.Messages` 中的 `Content` 保持为字符串（兼容内部处理），但新增 `ContentParts []ContentPart` 字段保存完整内容数组，供后端转发时重构原始消息格式。
  3. 在 `RawBody` 已保留完整请求的前提下，`MessageContent` 的解析主要影响内部日志和缓存 key 生成，不破坏后端透传。
- **验证方式（可执行）**：
  ```bash
  go test ./plugins/protocol/openai/ -run TestMessageContent_Vision -v
  go test ./plugins/protocol/openai/ -run TestParseRequest_VisionMessage -v
  ```
- **残余风险**：可接受

### R13 — 缓存 key 未纳入 P0 字段导致缓存污染

- **触发条件**：客户端 A 发送 `response_format=json_object`、客户端 B 发送 `response_format=text`，二者其余请求体相同（model/messages/temperature/max_tokens）。当前 `core/internal/cache/proxy_cache.go:78` `GetRequestKey(model, messages, temperature, maxTokens)` 不含 `response_format`/`tool_choice`/`seed` → 生成同一缓存 key → B 命中 A 的缓存（JSON 对象响应被当作普通文本返回）。
- **最坏结果**：语义/精确缓存返回不符 `response_format`/`tool_choice`/`seed` 预期的响应 → 下游 Agent 解析失败或行为错乱（如 LangChain 期待 JSON Schema 却收到散文）。
- **缓解措施（编码前可做）**：
  1. [G4/不可延后] `GetRequestKey` 增参 `responseFormat *ResponseFormatSpec, toolChoice interface{}, seed *int`（或改接收 `*plugin.ProxyRequest` 降低签名漂移）。
  2. `keyData` map 追加 3 字段的稳定序列化；`tool_choice` 为 `interface{}` 须 `json.Marshal` 取 hash（nil/对象/string 统一）。
  3. 同步更新所有调用点 + `NormalizeMessagesForKey` 路径保持预测接口与 `/v1/chat/completions` key 一致。
  4. 旧缓存因 key 变更全部失效——属预期，自测记录登记命中数 0 且不报错，不做回写兼容。
- **验证方式（可执行）**：
  ```bash
  go test ./core/internal/cache/ -run TestCacheKey_DiffersByResponseFormat -v
  go test ./core/internal/cache/ -run TestCacheKey_DiffersBySeed -v
  go test ./core/internal/cache/ -run TestCacheKey_DiffersByToolChoice -v
  go test ./core/internal/cache/ -run TestCacheKey_StableForSameInput -v
  rg 'GetRequestKey' ./core/internal/cache/ ./core/internal/proxy/  # 调用点签名一致性
  ```
- **残余风险**：可接受
