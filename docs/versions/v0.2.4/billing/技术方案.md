# 技术方案 — 计费功能

> 版本：v0.2.4 | 日期：2026-07-18 | 作者：AI  
> 修订：2026-07-18（对照代码真源复审：路径、既有模块、货币语义、API 边界）

## 1. 背景与目标

### 1.1 问题描述

Centag 作为 LLM 反向代理/网关，需要为用量提供可配置的成本归因能力。当前已具备：

| 已有能力 | 位置 | 局限 |
|----------|------|------|
| Token 计量与日聚合 | `core/internal/tokenusage/` | 成本来自硬编码价格表 |
| 硬编码价格表 | `core/pkg/scheduler/price_table.go` | 无法按环境动态调整 |
| 成本汇总 API | `GET /api/v1/admin/cost/summary`（`core/pkg/server/cost_handler.go`） | 依赖上述硬编码估算 |
| 异步计费事件钩子 | `core/internal/billing.Service`（EventHandler） | 仅事件分发，无规则引擎 |
| API Key 预算检查 | `core/internal/auth/budget.go` | 与本版本「规则定价」正交，不改动 |
| 用户/团队配额 | `tokenusage` 配额服务 | 已存在，本版本不重做 |

缺口集中在：**可配置计费规则 → 估算 → 落库明细 → 管理导入导出**。

### 1.2 目标

本版本（v0.2.4）实现：

1. **计费规则引擎**：按 `backend_id + model`（支持 `*`）定义输入/输出单价，支持优先级与启用开关  
2. **YAML 为配置真源之一**：`config/pricing/default.yaml` 预置；支持 import/export  
3. **Token 计量增强**：在现有 `token_usage.cost_usd` 写入路径上，用规则引擎替换硬编码估算；可选落库 `input_cost` / `output_cost` / `pricing_rule_id`  
4. **管理 API**：规则 CRUD + YAML 导入导出；成本查询**复用并增强**既有 `/api/v1/admin/cost/*`，不平行新建一套 costs API  
5. **三种发行版适配**（规则存储策略不同；用量沿用现有计量实现）：
   - **minimal**：规则驻留内存（启动加载 YAML）；用量沿用 `tokenusage.NewEphemeralService()`（进程内 SQLite，重启清零）  
   - **personal**：规则 YAML 种子 → SQLite；用量走既有 SQLite `token_usage`  
   - **team**：规则 YAML 种子 → PostgreSQL；用量走既有 PG `token_usage`

### 1.3 非目标

- ❌ 用户钱包 / 预付费充值 / 支付集成  
- ❌ 账单 / 发票生成  
- ❌ 用量预警 / 通知  
- ❌ 多租户差异化定价（租户级折扣）  
- ❌ Web 前端计费管理界面  
- ❌ 改造 `auth` 预算预检或配额扣减逻辑（已有能力保持不动）  
- ❌ 重写或替换现有 `billing.Service`（异步 Event 钩子）；本版本在其旁路新增**定价子系统**  
- ❌ 重命名历史列 `cost_usd`（见 §2.3 货币约定）

## 2. 方案选型

### 2.1 候选方案对比

| 方案 | 优点 | 缺点 | 推荐 |
|------|------|------|------|
| **A：仅扩展 tokenusage + price_table** | 改动面小 | 规则管理、YAML、多模式加载继续堆在计量包，边界更糊 | |
| **B：在 billing 包内新增定价子系统** | 与计量分离；复用包目录；钩子 Event 服务可并存 | 需避免与现有 `billing.Service` 类型名冲突 | ⭐ |
| **C：插件化计费** | 可插拔 | 本版本过度设计 | |

### 2.2 选定方案

选择 **方案 B**：在 `core/internal/billing/` 新增定价子系统，与现有事件服务共存：

| 类型（现有） | 类型（新增） | 职责 |
|--------------|--------------|------|
| `billing.Service` | （保留） | 异步 `Event` / `EventHandler` |
| — | `billing.PricingService` | 规则解析、成本估算、缓存失效 |
| — | `billing.RuleStore` | 规则持久化（Memory / SQL） |

理由：

1. 计费规则与 token 计量职责分离；`tokenusage` 只调用 `PricingService`  
2. 不破坏已接线的 `billingHookAdapter`  
3. 符合「网关基础能力进核心层」约束  
4. 管理 HTTP 层沿用现有惯例：放在 `core/pkg/server/`（与 `CostHandler` 一致），而非新建平行 handler 体系

### 2.3 定价与货币约定（强制）

**定价键**：`backend_id + model`（与 `ModelPriceTable`、业界实践一致）。

**公式**：

```text
input_cost  = input_tokens  / 1_000_000 * input_price_per_m
output_cost = output_tokens / 1_000_000 * output_price_per_m
total_cost  = input_cost + output_cost
```

**货币语义（本版本决策）**：

| 项 | 约定 |
|----|------|
| 规则 / 计量正本币种 | **`USD`**（YAML 导入导出默认 USD；单价与 `cost_usd` 均为美元） |
| 显示汇率 | `config/pricing/default.yaml` 的 `usd_to_cny`；前端选人民币时仅做显示换算 |
| DB 列名 `cost_usd` / JSON `cost_usd` | **历史命名保留**；语义即为 USD |
| API 增强 | 成本响应 `currency=USD` + `usd_to_cny` |
| `billing.Event.Amount` | 估算金额（USD）；Currency 写 `USD` |

> 导入旧版 `currency: CNY` 的 YAML 时，服务端按 `usd_to_cny` 换算为 USD 后入库。

### 2.4 与既有成本 API 的关系

| 既有 | 本版本动作 |
|------|------------|
| `GET /api/v1/admin/cost/summary` | **保留路径**；内部继续聚合 `token_usage.cost_usd`；响应增加 `currency` |
| 新建 `/api/v1/admin/billing/costs*` | **不做**（避免双入口） |
| 新建 `/api/v1/admin/billing/rules*` | **新增**（规则 CRUD + YAML import/export） |

## 3. 详细设计

### 3.1 模块架构

```
core/internal/billing/
├── billing.go              # 现有：Event / EventHandler / Service（异步钩子）
├── pricing_rule.go         # 新增：规则模型 + YAML 文件结构
├── rule_store.go           # 新增：RuleStore 接口
├── rule_store_memory.go    # 新增：minimal / 无 DB 时
├── rule_store_sql.go       # 新增：SQLite + PostgreSQL
├── yaml_loader.go          # 新增：加载 / 导入 / 导出
├── pricing_service.go      # 新增：PricingService（匹配、估算、缓存）
└── *_test.go

用量写入仍在：
  core/internal/tokenusage/     # RecordUsage / GetCostSummary / ephemeral
管理 HTTP 在：
  core/pkg/server/              # BillingRulesHandler + 增强 CostHandler
```

### 3.2 数据模型

#### 3.2.1 计费规则 YAML

```yaml
# config/pricing/default.yaml
version: "1.0"
currency: "USD"
usd_to_cny: 7.2
updated_at: "2026-07-18T00:00:00Z"

rules:
  - name: "Ollama 本地"
    backend_id: "ollama-local"
    model: "*"
    input_price_per_m: 0
    output_price_per_m: 0
    priority: 0
    enabled: true

  - name: "PPIO DeepSeek V3.2"
    backend_id: "ppinfra"
    model: "deepseek-v3.2"
    input_price_per_m: 1.0
    output_price_per_m: 1.0
    priority: 100
    enabled: true
```

字段语义与现网硬编码表对齐；完整种子列表见 §4.3。

#### 3.2.2 表 `pricing_rules`（personal / team）

```sql
CREATE TABLE IF NOT EXISTS pricing_rules (
    id BIGSERIAL PRIMARY KEY,                 -- SQLite: INTEGER PRIMARY KEY AUTOINCREMENT
    name VARCHAR(100) NOT NULL,
    backend_id VARCHAR(100) NOT NULL,
    model VARCHAR(100) NOT NULL,
    input_price_per_m DECIMAL(12,6) NOT NULL,
    output_price_per_m DECIMAL(12,6) NOT NULL,
    currency VARCHAR(3) DEFAULT 'USD',
    priority INT DEFAULT 0,
    enabled BOOLEAN DEFAULT true,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_pricing_rules_backend_model
    ON pricing_rules(backend_id, model);
```

迁移编号接续现网最新：`031_*`（当前最高为 `030_drop_user_request_logs`）。

#### 3.2.3 扩展 `token_usage`（可选明细列）

```sql
ALTER TABLE token_usage ADD COLUMN IF NOT EXISTS input_cost DECIMAL(12,6) DEFAULT 0;
ALTER TABLE token_usage ADD COLUMN IF NOT EXISTS output_cost DECIMAL(12,6) DEFAULT 0;
ALTER TABLE token_usage ADD COLUMN IF NOT EXISTS pricing_rule_id BIGINT;
-- 不建 FK：minimal ephemeral 与历史库无 pricing_rules 时仍可写用量
```

- **`cost_usd`**：继续写 `total_cost`（列名不变）  
- **`token_usage_daily.total_cost_usd`**：继续累加 total，本版本不新增 daily 拆分列  
- **ephemeral schema**（minimal）：同步追加上述三列，避免 minimal 写入失败

#### 3.2.4 规则加载策略

| 发行版 | 规则存储 | 用量存储（既有） | 加载 |
|--------|----------|------------------|------|
| minimal | Memory（YAML） | Ephemeral SQLite | 启动读 YAML；无 DB 规则表 |
| personal | SQLite `pricing_rules` | SQLite `token_usage` | DB 非空用 DB；空则 YAML 导入一次 |
| team | PostgreSQL `pricing_rules` | PG `token_usage` | 同上 |

YAML 作用：minimal 唯一规则源；personal/team 种子与备份迁移载体；可随版本发布。

### 3.3 接口设计

#### 3.3.1 内部 Go API（新增）

```go
// core/internal/billing/pricing_service.go

type PricingService interface {
    ResolvePrice(ctx context.Context, backendID, model string) (*PriceInfo, error)
    EstimateCost(ctx context.Context, backendID, model string, inputTokens, outputTokens int) (*CostBreakdown, error)
    InvalidateCache(ctx context.Context) error
}

type RuleStore interface {
    ListRules(ctx context.Context) ([]*PricingRule, error)
    GetRule(ctx context.Context, id int64) (*PricingRule, error)
    CreateRule(ctx context.Context, rule *PricingRule) error
    UpdateRule(ctx context.Context, id int64, rule *PricingRule) error
    DeleteRule(ctx context.Context, id int64) error
    ImportFromYAML(ctx context.Context, data []byte) error
    ExportToYAML(ctx context.Context) ([]byte, error)
}

type PriceInfo struct {
    InputPricePerM  float64 `json:"input_price_per_m"`
    OutputPricePerM float64 `json:"output_price_per_m"`
    Currency        string  `json:"currency"`
    PricingRuleID   int64   `json:"pricing_rule_id"` // 硬编码 fallback 时为 0
    Source          string  `json:"source"`          // "rule" | "legacy_table" | "default"
}

type CostBreakdown struct {
    InputCost    float64 `json:"input_cost"`
    OutputCost   float64 `json:"output_cost"`
    TotalCost    float64 `json:"total_cost"`
    Currency     string  `json:"currency"`
    InputTokens  int     `json:"input_tokens"`
    OutputTokens int     `json:"output_tokens"`
    PricingRuleID int64  `json:"pricing_rule_id"`
    Source       string  `json:"source"`
}
```

**用量记录不进 `RuleStore`**：继续由 `tokenusage.Service.RecordUsage` 负责，内部调用 `PricingService.EstimateCost`。

#### 3.3.2 管理 HTTP API

**规则（新增）**：

```
POST   /api/v1/admin/billing/rules
GET    /api/v1/admin/billing/rules
PUT    /api/v1/admin/billing/rules/:id
DELETE /api/v1/admin/billing/rules/:id
POST   /api/v1/admin/billing/rules/import
GET    /api/v1/admin/billing/rules/export
```

鉴权：挂既有 admin 路由组（与 `/api/v1/admin/cost/summary` 同级权限）。规则变更成功后调用 `PricingService.InvalidateCache()`。

**成本（增强既有，不新建平行路径）**：

```
GET /api/v1/admin/cost/summary   # 已有；增强 currency；group_by 能力保持
```

按日 / 按模型：继续用 `group_by=date|model`，**不**新增 `/billing/costs/daily` 等别名（文档中说明即可）。

### 3.5 流程图

#### 3.5.1 规则匹配

```
backend_id + model
        │
        ▼
查询启用规则：(backend_id=? OR '*') AND (model=? OR '*')
        │
        ▼
按 priority DESC；同分优先更具体匹配
（精确 model > model=*；精确 backend > backend=*）
        │
        ├─ 命中 → Source=rule
        ├─ 未命中 → legacy ModelPriceTable → Source=legacy_table
        └─ 表无条目 → 默认 0.7/0.7 USD → Source=default
```

#### 3.5.2 计量与计费

```
LLM 响应 → 提取 prompt/completion tokens
        │
        ▼
PricingService.EstimateCost(...)
        │
        ▼
tokenusage.RecordUsage：
  cost_usd = total_cost
  input_cost / output_cost / pricing_rule_id（若列存在）
        │
        ▼
（可选）billing.Service.RecordEvent 异步钩子 — 既有链路，金额与币种对齐
```

### 3.6 三种模式适配（规则侧）

| 模式 | RuleStore | 说明 |
|------|-----------|------|
| minimal | `MemoryRuleStore` | 启动加载 YAML；进程内 CRUD 不回写文件（export 可导出当前内存） |
| personal | `SQLRuleStore`（SQLite） | 首次空表导入 YAML |
| team | `SQLRuleStore`（PostgreSQL） | 同上 |

用量侧**不**新建 MemoryStore；minimal 继续用 ephemeral SQLite。

## 4. 兼容性与迁移

### 4.1 向后兼容

- 代理协议路径不变（`/v1/chat/completions` 等）  
- `cost_usd` 列名与既有统计 API 字段名保持  
- 无规则时 fallback 到 `ModelPriceTable`，行为接近现网  
- 现有 `billing.Service` 事件钩子链路保持可注册

### 4.2 数据迁移

```
031_pricing_rules.{postgresql,sqlite}.sql
032_token_usage_billing.{postgresql,sqlite}.sql
```

SQLite 无 `IF NOT EXISTS` 的 ADD COLUMN 时，按项目既有迁移风格做幂等/忽略重复（对齐 `019_cost_and_success.sqlite.sql` 惯例）。

### 4.3 初始化数据（YAML 种子）

与现网 `initDefaultPrices()` 对齐的核心条目（可按实现微调，但不得少于现网已覆盖后端）：

- ollama-local / `*` → 0/0  
- ppinfra：deepseek-v3.2、qwen3.5-plus、glm-5、kimi-k2.5、minimax-m2.5  
- bigmodel：glm-5、glm-4.7、glm-4-flash、glm-4-flashx  

完整内容写入 `config/pricing/default.yaml`，并以该文件为 T1 验收基准。

## 5. 风险与应对（方案级摘要）

| 风险 | 影响 | 概率 | 应对策略 |
|------|------|------|---------|
| 与现有 `billing.Service` 命名/职责混淆 | 集成错误 | 中 | 新 API 统一用 `PricingService` / `RuleStore` 前缀 |
| 显示币种与正本混淆 | 误做落库汇率换算 | 中 | 正本始终 USD；仅 UI 用 `usd_to_cny` 显示换算 |
| 规则缓存与 DB 不一致 | 短时错价 | 中 | TTL + 变更主动 `InvalidateCache` |
| 范围膨胀到钱包/鉴权改造 | 排期失控 | 中 | 非目标清单 + Gate 验收对照 |
| 平行 costs API 导致双入口 | 运维困惑 | 中 | 只增强既有 `/admin/cost/summary` |

详细开发风险见同目录 `开发风险评估.md`。
