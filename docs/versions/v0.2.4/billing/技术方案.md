# 技术方案 — 计费功能

> 版本：v0.2.4 | 日期：2026-07-17 | 作者：AI

## 1. 背景与目标

### 1.1 问题描述

Centag 作为 LLM 反向代理/网关，需要为用户提供虚拟额度管理能力。当前项目已有基础的 token 计量（`tokenusage/`）和计费事件接口（`billing/`），但缺少：

1. **计费规则的动态配置**：当前价格表硬编码在 `pkg/scheduler/price_table.go`，无法按后端、模型、用户等级动态调整
2. **不同模式的差异化存储**：minimal 模式无数据库，personal 模式用 SQLite，team 模式用 PostgreSQL，需要统一的计费接口适配三种存储策略
3. **完整的计费流程**：缺少费用估算、余额管理、账单查询等核心能力

### 1.2 目标

本版本（v0.2.4）实现以下核心能力：

1. **计费规则引擎**：支持按后端+模型定义输入/输出价格，支持动态配置
2. **Token 计量增强**：在现有 `token_usage` 基础上，集成计费规则进行成本估算
3. **统计查询 API**：提供按用户、模型、后端、日期维度的成本聚合查询
4. **三种模式适配**：
   - minimal：内存计费，重启清零
   - personal：SQLite 持久化
   - team：PostgreSQL 持久化 + 用户配额

### 1.3 非目标

以下能力不在本版本范围内：

- ❌ 用户钱包/余额系统（预付费充值）
- ❌ 支付集成（支付宝/微信支付）
- ❌ 账单/发票生成
- ❌ 用量预警/通知
- ❌ 多租户差异化定价（team 模式的租户级折扣）
- ❌ Web 前端计费管理界面

## 2. 方案选型

### 2.1 候选方案对比

| 方案 | 优点 | 缺点 | 推荐 |
|------|------|------|------|
| **方案 A：扩展现有模块** | 复用 `tokenusage/` 和 `billing/`，改动小 | 模块边界模糊，计费逻辑散落 | |
| **方案 B：独立计费模块** | 职责清晰，易于维护 | 需要重构部分现有代码 | ⭐ |
| **方案 C：插件化计费** | 灵活性最高，可插拔 | 复杂度高，本版本过度设计 | |

### 2.2 选定方案

选择 **方案 B：独立计费模块**，理由：

1. **职责清晰**：计费逻辑集中在 `internal/billing/` 下，与 `tokenusage/`（计量）分离
2. **复用现有基础**：`billing.go` 已定义 EventHandler 接口，可直接扩展
3. **支持三种模式**：通过接口抽象，minimal/personal/team 各自实现存储策略
4. **符合架构约束**：计费是所有 LLM 网关都需要的基础能力，应放在核心层

### 2.3 定价基础确认

**采用方案A：以模型为基础定价**，与业界主流实践一致：

- **定价单位**：`backend_id + model`
- **计费公式**：`总费用 = (input_tokens × input_price + output_tokens × output_price) / 1,000,000`
- **参考**：OpenAI、Anthropic、DeepSeek 等均采用此模式

选择理由：
1. **简单直观**：用户能清楚理解"调用哪个模型花了多少钱"
2. **与现有代码一致**：`pkg/scheduler/price_table.go` 已按 `backend_id + model` 定价
3. **易于维护**：只需维护一张价格表，无需复杂的流水线系数计算

#### 3.2.2 计费规则表（pricing_rules）— team 模式持久化

```sql
CREATE TABLE IF NOT EXISTS pricing_rules (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    backend_id VARCHAR(100) NOT NULL,          -- 后端ID，'*'表示匹配所有
    model VARCHAR(100) NOT NULL,               -- 模型名，'*'表示匹配所有
    input_price_per_m DECIMAL(12,6) NOT NULL,  -- 输入价格（元/1M tokens）
    output_price_per_m DECIMAL(12,6) NOT NULL, -- 输出价格（元/1M tokens）
    currency VARCHAR(3) DEFAULT 'CNY',         -- 货币单位
    priority INT DEFAULT 0,                    -- 优先级，越高越优先
    enabled BOOLEAN DEFAULT true,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_pricing_rules_backend_model 
    ON pricing_rules(backend_id, model);
```

#### 3.2.3 存储策略

| 发行版 | 存储方式 | 配置来源 | 说明 |
|--------|----------|----------|------|
| **minimal** | YAML 文件（仅内存） | `config/pricing/default.yaml` | 重启从文件加载，无持久化 |
| **personal** | YAML 文件 + SQLite | `config/pricing/default.yaml` → SQLite | 首次从 YAML 导入，后续读写 SQLite |
| **team** | YAML 文件 + PostgreSQL | `config/pricing/default.yaml` → PG | 首次从 YAML 导入，后续读写 PG |

**加载优先级**：DB 有数据 → 用 DB；DB 为空 → 从 YAML 导入

**YAML 文件的核心作用**：
1. **minimal 模式的唯一配置源**：无数据库，完全依赖 YAML 文件
2. **初始数据导入**：personal/team 模式首次启动时从 YAML 加载默认规则
3. **备份与迁移**：通过导出 YAML 实现规则的备份和跨环境迁移
4. **版本管理**：YAML 文件可随代码版本发布，便于回滚和切换

### 3.3 接口设计

#### 3.3.1 内部接口（Go API）

```go
// internal/billing/service.go

// Service 计费服务接口
type Service interface {
    // ResolvePrice 解析计费规则，返回输入/输出价格
    ResolvePrice(ctx context.Context, backendID, model string) (*PriceInfo, error)
    
    // EstimateCost 估算成本（元）
    EstimateCost(ctx context.Context, backendID, model string, inputTokens, outputTokens int) (*CostBreakdown, error)
    
    // RecordUsage 记录用量并计算成本
    RecordUsage(ctx context.Context, req *RecordUsageRequest) (*UsageRecord, error)
    
    // GetCostSummary 获取成本汇总
    GetCostSummary(ctx context.Context, query *CostSummaryQuery) (*CostSummary, error)
}

// PriceInfo 价格信息
type PriceInfo struct {
    InputPricePerM  float64 `json:"input_price_per_m"`   // 输入价格（元/1M tokens）
    OutputPricePerM float64 `json:"output_price_per_m"`  // 输出价格（元/1M tokens）
    Currency        string  `json:"currency"`
    PricingRuleID   int64   `json:"pricing_rule_id"`     // 命中的规则ID
}

// CostBreakdown 成本明细
type CostBreakdown struct {
    InputCost      float64 `json:"input_cost"`        // 输入成本
    OutputCost     float64 `json:"output_cost"`       // 输出成本
    TotalCost      float64 `json:"total_cost"`        // 总成本
    Currency       string  `json:"currency"`
    InputTokens    int     `json:"input_tokens"`
    OutputTokens   int     `json:"output_tokens"`
}
```

### 3.5 流程图

#### 3.5.1 计费规则匹配流程

```
请求到达
    │
    ▼
┌─────────────────────────────────────┐
│ 1. 提取 backend_id + model          │
└─────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────┐
│ 2. 查询 pricing_rules               │
│    WHERE (backend_id = ? OR '*')    │
│    AND (model = ? OR '*')           │
│    AND enabled = true               │
│    ORDER BY priority DESC           │
└─────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────┐
│ 3. 命中规则？                        │
│    是 → 返回规则价格                 │
│    否 → 返回默认价格（5.0/5.0）      │
└─────────────────────────────────────┘
```

#### 3.5.2 Token 计量与计费流程

```
LLM 响应返回
    │
    ▼
┌─────────────────────────────────────┐
│ 1. 提取 token 使用量                 │
│    prompt_tokens + completion_tokens │
└─────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────┐
│ 2. 调用 billing.Service             │
│    EstimateCost(backend, model, ...)│
└─────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────┐
│ 3. 写入 token_usage                 │
│    含 cost_usd + input_cost +       │
│    output_cost + pricing_rule_id    │
└─────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────┐
│ 4. 发送 billing.Event               │
│    (异步，用于扩展)                  │
└─────────────────────────────────────┘
```

## 4. 兼容性与迁移

### 4.1 向后兼容

- **现有 API 不变**：`/v1/chat/completions` 等代理接口无变化

## 5. 风险与应对

| 风险 | 影响 | 概率 | 应对策略 |
|------|------|------|---------|
| 价格表缓存一致性 | 计费不准 | 中 | 使用 TTL 缓存（5分钟），规则变更时主动失效 |
| 并发写入 token_usage | 数据丢失 | 低 | 使用数据库事务，已有实现 |
| minimal 模式内存溢出 | 服务崩溃 | 低 | 限制最大记录数（10万条），LRU 淘汰 |
| 硬编码价格表与 DB 规则冲突 | 计费混乱 | 中 | DB 规则优先，硬编码作为 fallback |
| SQLite 并发性能 | 查询慢 | 中 | personal 模式为单用户，并发低 |
